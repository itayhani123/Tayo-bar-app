## הפעולה הבאה — בדיקה בלבד

1. פתחו את פרויקט Supabase Production הנכון.
2. פתחו SQL Editor וצרו שאילתה חדשה.
3. בחרו תפקיד postgres, אם מוצג בורר תפקידים.
4. העתיקו את כל docs/sql/033-event-selection-preflight.sql, בלי קובץ אחר.
5. לחצו Run פעם אחת.
6. העבירו את 16 השורות: check_name, status, details. אין בפלט טלפונים, שמות או סודות.
7. עצרו והמתינו לאישור להתקנה. אין להריץ את המיגרציה בשלב זה.

תוצאה תקינה: בדיוק 16 PASS — שש פונקציות, שבע עמודות, buttons_policy,
033_not_installed ו־receipt_dedupe. אין WARNING בקובץ הזה.
כל FAIL, שגיאת SQL, שורה חסרה או תוצאה שונה מחייבים עצירה ובדיקה.
אם 033_not_installed נכשל, אין להריץ שוב או למחוק פונקציה; בודקים אם כבר הותקנה
גרסה כלשהי ומריצים אימות מתאים. לא משנים הרשאות/חתימות רק כדי לקבל PASS.

## התקנה בעתיד — רק באישור מפורש נוסף

1. אמתו ב־Vercel את ה־commit הפעיל ואת Production Branch, וב־Supabase את יעד
   APP_URL של ה־Edge ואת מפעילי ה־Worker. אם חסר תיקון פעיל בענף, עוצרים ומשווים.
2. ודאו שיתאפשר מעבר מתואם של Webhook ו־Worker לאותה גרסה. בזמן המעבר יתואם
   ניקוז/השהיית עיבוד עם האחראי; Webhook הקליטה נשאר זמין. לא בוצעה השהיה כאן.
   אסור ש־Worker ישן יקבל דיווח שחזר לתור לאחר בחירת אירוע, כי הוא לא מכיר את הבחירה.
3. הריצו שוב preflight סמוך להתקנה ודירשו 16 PASS.
4. הריצו רק supabase/migrations/033_whatsapp_attendance_event_selection.sql, במלואו,
   בטרנזקציה שבתוכו. כל שגיאה מחייבת עצירה; בודקים rollback ולא עוקפים הגנות.
   CREATE מגן מפני דריסה/overload לא מוכר; זו אינה מיגרציה להרצה חוזרת עיוורת.
5. הריצו docs/sql/033-event-selection-verify.sql במלואו. נדרשות בדיוק שתי שורות PASS
   עבור שתי הפונקציות החדשות, כולל MD5, search_path ו־EXECUTE ל־service_role בלבד.
6. תעדו את התקנת 033 בתהליך המיגרציות המאושר בלי להפעיל או לסמן 029–032 שלא הותקנו.
7. רק אחרי אימות SQL מוצלח, פרסו מה־commit המדויק של ענף הפיצ׳ר. לפני push בדקו
   שהענף אינו Production Branch ושאין אוטומציה שמקדמת אותו. אין merge ל־main כחלק
   אוטומטי מההוראות. בנו Production מדורג בלי החלפת דומיין ואמתו READY ומקור.

   vercel deploy --prod --skip-domain --meta feature=whatsapp-event-choice --meta sourceCommit=<FULL_FEATURE_COMMIT>

   מריצים מתוך worktree נקי ומקושר לפרויקט/צוות הנכונים. פקודה זו יוצרת Deployment
   בסביבת Production אף שאינה מעבירה דומיין. סודות נשארים בהגדרות הסביבה, לא בפקודה.
8. אחרי בדיקות ואישור לקידום, קדמו את ה־Deployment המזוהה לדומיין היציב. ודאו ש־Cron
   וה־Edge פונים לכתובת הזאת, ולא לכתובת Deployment ישנה; המימוש משתמש ב־Edge הקיימת
   ואינו דורש מערכת WhatsApp נוספת.
9. חדשו עיבוד רק לאחר שכל המפעילים מגיעים לגרסה החדשה, ובצעו את בדיקות ההצלחה.

## בדיקות הצלחה

- התאמה אחת: סיכום ואישור רגילים, ללא בחירת אירוע נוספת.
- שתי התאמות: רשימה עם אולם/תאריך/סוג/לקוח; אפשר מספר או כפתור; אין שעות לפני הבחירה.
- אחרי בחירה: מתקבל סיכום חדש. אין שעות עד לחיצה על כפתור אישור השעות הקיים.
- מספר שגוי: הודעה ברורה, ניתן לבחור שוב; תוקף שפג: רשימה חדשה.
- כמה רשימות: מספר ללא הקשר אינו בוחר ברשימה אחרת; תגובה מצוטטת או כפתור כן.
- ביטול לפני ואחרי בחירה: אין שמירה חדשה. אישור/מסירת הודעה חוזרים אינם שומרים שוב.
- אין התאמה: בקשת פרטים ללא אירועים לא קשורים.

אם פריסת קוד נכשלת אחרי SQL: הפונקציות החדשות יכולות להישאר מותקנות ללא שימוש
בקוד הישן. לא מריצים DROP או שינוי לפונקציות השמירה הקיימות. אחרי שרשימות כבר
נוצרו אין לחזור ל־Worker ישן על דיווחי הבחירה הפעילים; משהים עיבוד באישור ומתקנים
קדימה. שומרים קליטה ותורים ולא מאפסים/מאשרים דיווחים באופן גורף.
