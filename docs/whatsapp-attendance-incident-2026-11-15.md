לפיכך **אין כאן הוכחה שאישור לדיווח של 19:46 פג כעבור ארבע דקות**.
השגיאה נוצרה בעיבוד תגובה לסיכום ישן. הפונקציה הקודמת איחדה אסימון שונה,
תוקף שפג ומצב דיווח שהשתנה להודעת expired אחת, ולכן אי אפשר לשחזר מהנתונים

את סוג הודעת המקור; התאמת האסימון מוכיחה את הדיווח והסיכום, **לא מוכיחה
שהתגובה הגיעה בלחיצה ולא בפקודת טקסט**. לא נשמר raw webhook לבדיקה בדיעבד.

באותו זמן הדיווח הישן ניסה להתעבד שלוש פעמים ונכשל ב־`PROCESSING_FAILED`.
בתיעוד השליחות ניכר מחזור עיבוד של כחמש דקות. בקוד הישן מטופל דיווח אחד
בכל קריאת cron, מסודר לפי זמן הקליטה המקורי; דיווח ישן שחוזר לניסיון יכול
לצרוך שוב ושוב את סבב העיבוד. חריגה בשלב אחד גם עצרה את השלבים הבאים.
זו התאמה ישירה להצטברות שנמצאה. SQL guard של גרסת 025 קיים במסד, בעוד
הרשומות והסיכומים הישנים אינם נושאים marker של הקוד החדש. פער קוד/סכמה
הוא חשד מבוסס, אך **החריגה המקורית נמחקה בלוג הגנרי ואין הוכחה שזה היה
קוד השגיאה בפועל**. יש לאמת את גרסת Vercel ואת APP_URL של ה־Edge Function.

בדיקת catalog לקריאה בלבד מצאה אולם אחד, אירוע אחד בתאריך המפורש 2026-11-15
באותו אולם, ועובד פעיל אחד לכל אחד משני השמות שנמסרו. לא הודפסו קטלוגים,
טלפונים, שכר, טוקנים או מפתחות.

## תיקון הקוד

- מתזמן התורים מטפל בכמה דיווחים בכל הפעלה, משלב decisions/outbox/inbox,
  מבודד כשל בכל שלב ושומר זמן לתשובות. בחירת inbox לפי `available_at`
  מונעת מניסיון חוזר ישן לעקוף שוב ושוב הודעות שכבר ממתינות.
- דיווח חדש עם message ID חדש מקבל רשומת inbox חדשה. אותה העברת Webhook
  עם אותו ID עדיין מנוטרלת. לא שונתה מדיניות dedup לפי מזהה הספק.
- הצעות pending נקשרות לדיווח. כאשר register משותף מחזיר הצעה pending
  של דיווח אחר, נוצרת הצעה פרטית נפרדת עם אותו snapshot ותוכן. הצעה שכבר
  הצליחה ושעותיה עדיין תואמות יכולה להישאר משותפת, לשמירת idempotency.
- מסד הנתונים מגדיר תוקף של 600 שניות לאחר אישור השליחה הסופית של הכפתורים.
  ack, זמן השליחה והתוקף נשמרים אטומית, לפי `clock_timestamp()` בשרת.
  אין תלות בשעון הדפדפן או באזור הזמן שלו.
- בדיקת התוקף מסתמכת על `received_at` של החלטת הכפתור, שנקבע ב־PostgreSQL.
  לחיצה שנקלטה בזמן אינה נפסלת בגלל המתנה בתור. להצעה pending מבודדת
  ניתנת ארכת ביצוע פנימית קצרה, ורק לאחר בדיקת ההרשאה/האסימון והתוקף.
  בדיקות snapshot, חפיפות, עובדים פעילים ושמירה אטומית נשארות בזמן הכתיבה.
  גם הצעה שכבר הצליחה נבדקת מול השעות הנוכחיות לפני החזרת הצלחה לדיווח
  חדש. תגובת כפתור מהירה שמגיעה לפני commit של אישור השליחה ממתינה בתור
  במקום להיכשל או לצרוך ניסיונות התאוששות.
- `source_type=interactive.button_reply` ו־reply context נשמרים בהחלטה.
  context שסופק חייב להתאים להודעה היוצאת של הסיכום. UUID וקודי טקסט
  אינם מוצגים למשתמש או משמשים לאישור. הכפתורים: "אשר ושמור" ו־"ביטול".
- נתמכת רשימת טווחים ללא כותרות, למשל `שם 12:30-17:35`. OpenAI Structured
  Outputs עדיין מפענח את הכותרת; שמות ושעות בטווחים מוחזרים מהמקור באופן
  דטרמיניסטי. `17:3` נעצר לפני קריאת המודל ומייצר הודעת תיקון בתור הקיים,
  עם dedupe לדיווח. לא נוצרת נוכחות חלקית.
- לוגים בטוחים כוללים message/report/receipt/decision IDs, שלב, מספר ניסיון,
  policy, קוד DB או HTTP מספרי בלבד. אין raw errors, תוכן, טלפונים או סודות.
  כשל שליחה נשמר ונראה באפליקציה; אין fallback של כפתורים לטקסט.

אין יצירת עובדים או אירועים, שינוי בהרשאות כלליות, או שינוי בלוגיקת שכר.
לא נעשה reset או מחיקה של דיווחים ותורים קיימים.

## מיגרציה, פריסה ובדיקת Production אחרי אישור

1. לעיין ב־`supabase/migrations/026_whatsapp_attendance_reliability.sql`
   וב־`supabase db push --dry-run` מול הפרויקט הנכון. נדרשות 019–025 שכבר
   הוחלו, ואז 026 בלבד. היא מוסיפה שני שדות מקור להחלטות ופונקציות שרת
   פרטיות, ללא שינוי גורף ברשומות קיימות. כל RPC חדש מבטל PUBLIC/anon/
   authenticated execution ומורשה רק ל־service_role באותה טרנזקציה.
2. אחרי אישור להחלה, להחיל 026 ולפרוס את כל הקוד לאותו פרויקט Vercel.
   לא להסתפק בהחלת SQL כשה־worker הפרוס עדיין ישן. אין משתני סביבה חדשים.
3. לבדוק שה־Edge Function הקיים `whatsapp-notifications` משתמש ב־APP_URL
   של כתובת Production העדכנית, ובאותו CRON_SECRET. לא להדפיס אותם.
   לבדוק את לוח הזמנים של **ה־job הקיים** ולהפעילו כל דקה אם התשתית מאפשרת;
   לא ליצור cron מתחרה. התזמון בפועל לא שונה במסגרת המימוש.
4. להריץ בדיקת סכמה ו־trace לקריאה בלבד עם משתני הסביבה המתאימים:

   ```powershell
   node --env-file=.env.local scripts/check-whatsapp-attendance-schema.mjs
   node --env-file=.env.local scripts/diagnose-whatsapp-attendance.mjs
   ```

5. לוודא ששלושת הדיווחים הממתינים מקבלים ניסיונות עיבוד ותשובה דרך התור
   הקיים, בלי למחוק או לשנות ידנית את סטטוסיהם. לחפש בלוג לפי report ID.
   ה־worker החדש מדווח `buttons_attendance_v2`. שגיאת policy, DB או OpenAI
   צריכה להיות נראית עם שלב וקוד בטוחים במקום הודעה גנרית בלבד.
6. להכין אירוע בדיקה ועובדים ללא חפיפות, לשלוח הודעה עם טווחים, ואז לשלוח
   שוב לאחר ארבע דקות. שני message IDs צריכים לקבל סיכומים נפרדים.
   ביטול אחד אינו מבטל את האחר; אישור יוצר שיבוץ חסר ושעות, והודעת הצלחה
   נשלחת רק אחרי שהמסד אישר. אין לנסות זאת על שעות אמיתיות ללא כוונה לשמור.
7. לבדוק ארבע דקות, מעבר ל־10 דקות, כפתור ישן, שני עובדים ו־`17:3`.
   לכשל שליחה להסתכל ב־receipts ובמסך הדיווחים: אין הצלחה או אישור זמין
   כשהשליחה לא אומתה. לא להפעיל קריאת cron ידנית למטרת אבחון לקריאה בלבד,
   משום שהיא מעבדת תורים וכותבת נתונים.

הבדיקות האוטומטיות הן עם PostgreSQL מקומי ו־fetch מדומה. לא בוצעה החלה
מרוחקת, פריסה או שליחת הודעות אמיתיות במסגרת התיקון.
