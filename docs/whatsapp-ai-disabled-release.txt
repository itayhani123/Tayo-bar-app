הכנת Commit ופריסה - רק אחרי אישור נפרד
6. לבצע git fetch origin בענף המבודד; לוודא origin/main עדיין בבסיס המאושר.
7. להשתמש ברשימת changed_files שב-manifest החיצוני כדי להוסיף רק קבצים מאושרים.
   לא להשתמש ב-git add . או git add -A. לבדוק git diff --cached --name-status.
   ליצור Commit רק לאחר אישור; לשמור את ה-SHA המלא ולעמת את תוכנו עם ה-manifest.
8. לבצע push לענף הפיצ'ר בלבד אחרי אימות יעד האוטומציה; לא לעדכן main בשלב זה.
9. ליצור checkout מבודד ונקי מה-Commit שאושר, עם כל התלויות לפי package-lock.
   לא לפרוס מהתיקייה הראשית המלוכלכת או מתוך גיבוי המכיל קובצי אבחון מקומיים.
   לבדוק שוב SHA-256 של כל changed_files מול החבילה; אין שינוי קוד נוסף.
   ב-checkout רגיל מותר להשוות normalized_lf_sha256 לקובצי טקסט רגילים בלבד:
   ההבדל המותר היחיד הוא CRLF מול LF. ב-fixture של Production חובה SHA-256
   גולמי זהה: .gitattributes משמר אותו ללא המרת סיומות שורה.
10. להתקין/להשתמש ב-Vercel CLI ולחבר את ה-checkout לפרויקט ולצוות הנכונים
    ב-vercel link. אין Vercel CLI מחובר ומאומת בסביבת ההכנה הנוכחית.
    לא להריץ env pull, לא לשנות משתני סביבה, ולא להציג מפתחות בלוגים.
11. מתוך ה-checkout המאומת, פקודת הפריסה המדורגת היא:
      vercel deploy --prod --skip-domain
    היא משתמשת בסביבת Production אך אינה מקדמת את הדומיין הפעיל.
    אין להשתמש ב---env להפעלת AI, ב---public, ב-SQL או ב-deploy של Edge Functions.
12. לשמור Deployment ID ו-URL. להריץ vercel inspect <STAGED_DEPLOYMENT_URL>
    ולבדוק גם ב-Dashboard: Ready, הפרויקט/הצוות הנכונים ו-Source Commit המדויק.
    metadata שמוזן ידנית אינו הוכחה למקור. אם המקור אינו ניתן לאימות, לעצור.
13. לבדוק מסכי קריאה וכניסה בפריסה המדורגת. אין להפעיל Cron/Worker כבדיקה,
    ואין לשלוח הודעות בדיקה חתומות שייצרו דיווחים עסקיים ללא אישור נפרד.
    הדומיין הפעיל וה-Cron ממשיכים לשרת את הגרסה הקיימת בשלב זה.
14. לעצור לפני Promote ולהציג את התוצאות. רק באישור נפרד:
      vercel promote <STAGED_DEPLOYMENT_URL>
    לא לבצע במקביל merge/push ל-main שעלול ליצור פריסת Production נוספת.
15. לאחר קידום מאושר: לאמת Current/Ready, מקור, דגל כבוי ולוגי תנועה רגילה.
    לא להפעיל AI, לא ליצור Allowlist ולא להתקין 034 כחלק מהשלב הזה.

Rollback מדויק לפריסה המכובה בלבד
לפני קידום: להשאיר את הדומיין בגרסה הנוכחית; אין צורך בשינוי SQL או נתונים.
אחרי קידום: באישור מפורש לבצע Instant Rollback דרך Dashboard ל-Deployment
הקודם שנרשם בשלב 1, או:
  vercel rollback <PREVIOUS_PRODUCTION_DEPLOYMENT_URL>
לוודא Current/Ready, Source 640d299 ודיווחים תקינים. אין להחזיר נתוני מלאי/שעות
למצב קודם, ואין להריץ DROP/שינוי פונקציות/התקנה של מיגרציות.
התרחיש בטוח מבחינת הסכמה כי שלב זה אינו מתקין 034 ואינו יוצר משימות AI.
אם 034 הותקנה או AI הופעל בניגוד לתוכנית, לעצור ולהשתמש בנוהל נפרד;
אין להחיל את הנחת ה-rollback הזאת על משימות AI פעילות.
לאחר rollback Vercel עשוי לעצור auto-assignment; אין לשנות הגדרה זו ללא אישור.
