# תיקון WHATSAPP_COLUMN_MISSING לאחר הרחבת הבוט

התקלה נגרמת ב־GET `/api/whatsapp/attendance`, לאחר שנמצאו דיווחים:

```sql
select inbox_id, status, error_code, kind, created_at
from public.whatsapp_attendance_receipts
order by created_at desc;
```

הגרסה החדשה דורשת `created_at`, אך 020 ו־022 אינן מוסיפות אותה.
לכן החלת כל המיגרציות עד 022 אינה מספיקה. זו השמטה בקוד/מיגרציות,
ולא עדות לכך שהמיגרציות הקודמות לא הוחלו.

בבדיקת קריאה בלבד מול החיבור שב־`.env.local`, השאילתה וקריאת העמודה
הבודדת החזירו `42703` (undefined_column). יתר עמודות מנגנון WhatsApp
שבסקריפט ופונקציות הבוט היו זמינות. אימות admin עבר וגישה אנונימית נחסמה
עם `42501`, כמצופה. לא נקראו רשומות נוכחות בבדיקה זו.

מזהה התקלה שסופק: `2fd700c6-9656-4f62-85d9-6731956553a6`.
לא נקרא לוג Vercel היסטורי עבור מזהה זה. בדיקת Vercel לקריאה בלבד לא
מצאה אישור התחברות מקומי, ולכן **לא אומתה זהות פרויקט Supabase של
הפריסה הפעילה מול החיבור המקומי**. עצם חוסר העמודה משוחזר גם כאשר 022
הוחלה כראוי; אין צורך בהשערת פרויקט שגוי כדי להסביר את הכשל.

## התיקון

`supabase/migrations/023_whatsapp_receipt_created_at.sql` מוסיפה
`created_at timestamptz not null default now()`.
לרשומות היסטוריות שלא תועד להן זמן יצירה היא משתמשת ב־`message_at` הקיים.
זהו זמן מקור ההודעה, ולא זמן מסירה היסטורי משוחזר. היא אינה משנה תוכן,
טלפון, סטטוס, ניסיונות שליחה או נתוני נוכחות; היא מרעננת את מטמון PostgREST.
הפעלתה החוזרת נבדקה ללא אובדן נתונים. 020–022 נשארו ללא שינוי.

האבחון החדש בלוג השרת כולל requestId, operation=`read_receipts`,
databaseCode, databaseTable, databaseColumns ושם עמודה חסרה כאשר הוא
מזוהה ברשימה מאושרת. אין הודעות SQL גולמיות, מספרי טלפון או סודות בלוג.
`WHATSAPP_COLUMN_MISSING` ממופה רק ל־`42703` או `PGRST204`.
שגיאות הרשאות, אימות, חיבור ו־timeout נשארות מסווגות בנפרד.

## הפעלה ובדיקה אחרי אישור

1. לוודא שפרויקט Supabase המקושר הוא זה ש־Vercel Production משתמש בו.
   אין להדפיס מפתחות. אפשר להריץ את סקריפט האבחון בסביבות המתאימות
   ולהשוות `supabaseEndpointFingerprint`; השוואת שמות משתני סביבה לבדה
   אינה מוכיחה שהפרויקטים זהים.
2. לבדוק `supabase db push --dry-run`: יש להחיל את 023 החדשה בלבד מתוך
   המיגרציות שטרם הוחלו, ולא להריץ מיגרציות קודמות מחדש. לאשר כל שינוי
   Production לפני `db push` או הפעלת SQL.
3. להחיל 023 בפרויקט הנכון. **תיקון התקלה הנוכחית דורש שינוי סכמה;
   Redeploy לבדו לא יוסיף עמודה.** לפריסת האבחון המשופר נדרש גם Redeploy.
4. להריץ בדיקת קריאה בלבד עם החיבור המתאים:

   ```powershell
   node --env-file=.env.local scripts/check-whatsapp-attendance-schema.mjs
   ```

   כל בדיקות העמודות צריכות לעבור, כולל `created_at`. הסקריפט בודק את
   כל עמודות inbox/receipts/decisions שבוט הנוכחות משתמש בהן ושמות RPCs,
   ללא הדפסת נתונים. fingerprint ו־JWT ref הם בדיקות עזר בלבד;
   מפתחות שאינם JWT או כתובת מותאמת עשויים להחזיר התאמת פרויקט `null`.
5. לפתוח את מסך הדיווחים כשקיים לפחות דיווח אחד ולוודא GET עם HTTP 200,
   כולל היסטוריית דיווחים. לבדוק אישור וביטול בדיווח בדיקה ושסטטוס תוצאת
   השליחה מופיע. אם יש כשל נוסף, לחפש בלוג לפי requestId החדש.

לא הוחלה מיגרציה מרוחקת ולא בוצעה פריסה במסגרת תיקון זה.
